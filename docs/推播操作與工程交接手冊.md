# iTag 推播操作與工程交接手冊

本手冊供後續負責發送住戶通知與串接推播的工程師使用。正式環境以卡號尋找已註冊的 Android 或 iOS 裝置，再由 Firebase Cloud Messaging 發送通知。2026 年 10 月 9 日已完成 Android、iOS、外網 API、TCP 推播及 Firebase 發送驗收。

## 正式環境連線資訊

| 用途 | 位址 | 協定 |
|---|---|---|
| 發送推播 | `211.23.22.158:7002` | TCP，UTF-8 JSON Lines |
| App 裝置註冊 | `http://211.23.22.158:7004` | HTTP JSON API |
| 系統維護 | `211.23.22.158:7003` | SSH |
| 健康檢查 | `http://211.23.22.158:7004/health` | HTTP GET |

`7002` 與 `7004` 目前沒有 TLS。Socket secret、API key、Firebase 金鑰與登入密碼不得寫入程式碼、文件、工單或版本庫，應由系統管理者以安全方式提供。

## 使用圖形測試工具發送

macOS 測試工具位於推播服務器專案目錄：

```text
開啟推播測試工具.command
```

操作流程：

1. 雙擊啟動檔，瀏覽器會開啟 `http://127.0.0.1:8765`。
2. 上方狀態必須顯示已連線至 `211.23.22.158:7002`。
3. 輸入完整卡號、推播標題與內容。
4. 按下「傳送推播」。
5. 成功時會顯示通知 ID 與目標裝置數量。

測試資料目前包含：

| 平台 | 測試卡號 |
|---|---|
| Android | `AACC0102030405` |
| iOS | `AACC01020304` |

卡號採完全相符比對。輸入錯誤、長短不同或該卡號尚未註冊時，服務器會回覆 `no active devices found for card_number`。

## 使用 TCP Socket 串接

每個請求是一行 UTF-8 JSON，結尾必須包含換行字元 `\n`。單行上限為 64 KiB；同一個 TCP 連線可以連續送出多行請求。

請求格式：

```json
{"secret":"由管理者提供","card_number":"AACC0102030405","title":"包裹通知","body":"您的包裹已送達管理室。","data":{}}
```

欄位限制：

| 欄位 | 必填 | 限制 |
|---|---|---|
| `secret` | 是 | 至少 16 字元，必須符合服務器設定 |
| `card_number` | 是 | 1 至 128 字元，須與 App 註冊卡號完全相同 |
| `title` | 是 | 1 至 200 字元 |
| `body` | 是 | 1 至 4096 字元 |
| `data` | 否 | JSON object，預設為空物件 |

成功回覆：

```json
{"ok":true,"notification_id":"UUID","target_count":1}
```

Python 串接範例：

```python
import json
import os
import socket

host = "211.23.22.158"
port = 7002
secret = os.environ["IDTAG_SOCKET_SECRET"]

request = {
    "secret": secret,
    "card_number": "AACC0102030405",
    "title": "包裹通知",
    "body": "您的包裹已送達管理室。",
    "data": {},
}

with socket.create_connection((host, port), timeout=10) as connection:
    connection.sendall(
        json.dumps(request, ensure_ascii=False).encode("utf-8") + b"\n"
    )
    response = connection.makefile("rb").readline(65537)

result = json.loads(response.decode("utf-8"))
if not result.get("ok"):
    raise RuntimeError(result.get("error", "推播請求失敗"))

print(result["notification_id"], result["target_count"])
```

只有收到 `ok: true` 且 `target_count` 大於 0，才表示工作已成功加入佇列。這不等於使用者已看到或讀取通知。

## HTTP 發送介面

內部系統也可呼叫 `POST /v1/push`。請求需帶 `X-API-Key`，金鑰由管理者提供。

```bash
curl -X POST http://211.23.22.158:7004/v1/push \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: YOUR_API_KEY' \
  -d '{"card_number":"AACC0102030405","title":"包裹通知","body":"您的包裹已送達管理室。","data":{}}'
```

正式串接優先使用單一介面。既有客戶端若採 TCP 7002，可繼續使用，不需要同時呼叫 HTTP 介面。

## 常見回覆與處理方式

| 回覆或現象 | 原因 | 處理 |
|---|---|---|
| `unauthorized` | Socket secret 錯誤 | 重新取得正式 secret，不要反覆猜測 |
| `invalid request` | JSON、欄位或換行格式錯誤 | 檢查 JSON 與必填欄位 |
| `no active devices found for card_number` | 卡號無有效裝置 | 確認 App 卡號及推播註冊狀態 |
| `Connection refused` | NAT、Port Forward 或服務未監聽 | 依序檢查 Zyxel、Windows、Ubuntu 及 systemd |
| `target_count: 1` 但手機沒顯示 | FCM 接受不等於手機展示 | 檢查通知權限、網路、前景／背景狀態與系統通知設定 |

## 維運檢查指令

外網健康檢查：

```bash
curl http://211.23.22.158:7004/health
nc -vz 211.23.22.158 7002
ssh -p 7003 xiyi@211.23.22.158
```

服務狀態與紀錄：

```bash
sudo systemctl status idtag-push --no-pager
sudo journalctl -u idtag-push -n 100 --no-pager
sudo journalctl -u idtag-push -f
```

查看已註冊裝置：

```bash
sudo -u postgres psql -d idtag_push
```

```sql
SELECT platform, card_number, active, last_seen_at
FROM devices
ORDER BY updated_at DESC;
```

查看失敗工作：

```sql
SELECT id, card_number, title, status, attempts, next_attempt_at, created_at
FROM notifications
WHERE status = 'failed'
ORDER BY created_at DESC;
```

正常完成的通知及 delivery 明細會自動刪除，因此空佇列通常代表已處理完成，不是沒有傳送。

## 發版前驗收清單

- `GET /health` 回覆 `{"status":"ok"}`。
- 測試工具顯示已連線至 `211.23.22.158:7002`。
- Android 與 iOS 裝置都在 `devices` 表中且 `active = true`。
- Android 與 iOS 各送一則通知，回覆 `target_count` 大於 0。
- 服務紀錄顯示 Firebase HTTP v1 回覆 `HTTP/2 200 OK`。
- `notifications` 沒有殘留 `failed` 工作。
- 由實機使用者確認通知實際顯示；服務器本身只能確認 Firebase 已接受。
