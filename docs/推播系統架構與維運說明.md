# iTag 推播系統架構與維運說明

iTag 推播系統接收住戶 App 的 Firebase token，依完整卡號建立傳送工作，再透過 Firebase Cloud Messaging 將通知送至 Android 或 iOS。正式服務部署於 Ubuntu VM，外部流量經 Zyxel 防火牆與 Windows 主機轉送。

## 網路架構

```text
Android / iOS App
        │ HTTP 7004：註冊卡號與 Firebase token
        ▼
211.23.22.158（Zyxel USG20W-VPN）
        │ NAT / Port Forward
        ▼
Windows 主機 172.10.1.153
        │ Port Forward
        ▼
Ubuntu VM 172.10.1.51
  ├─ 7002  TCP 推播接收
  ├─ 7003  SSH 維護
  ├─ 7004  FastAPI 裝置註冊與健康檢查
  └─ 5432  PostgreSQL，僅本機
```

外網正式端口：

| 外網端口 | 最終目的 | 用途 |
|---|---|---|
| 7001 | Ubuntu SSH 22 | 客戶現有轉送路由，不供 App 使用 |
| 7002 | Ubuntu 7002 | 接收推播 JSON |
| 7003 | Ubuntu 7003 | 系統維護 SSH |
| 7004 | Ubuntu 7004 | App API 與健康檢查 |

Port Forward 任一層失效時，外部會出現逾時或 `Connection refused`。排查順序為 Zyxel NAT、Windows Port Forward、Ubuntu 監聽端口、`idtag-push` systemd 服務。

## 應用服務架構

```text
Flutter App ── POST /v1/devices ─┐
                                 │
工程系統 ── TCP 7002 ───────────┼── Python idtag-push
工程系統 ── POST /v1/push ──────┘         │
                                          ▼
                                      PostgreSQL
                              devices / notifications / deliveries
                                          │
                                      Push Worker
                                          │ Firebase HTTP v1
                                          ▼
                                  Firebase Cloud Messaging
                                    ├─ Android 裝置
                                    └─ APNs → iOS 裝置
```

主要元件：

| 元件 | 職責 |
|---|---|
| FastAPI | 健康檢查、裝置註冊、取消註冊及 HTTP 推播入口 |
| TCP Socket Server | 接收以換行分隔的 JSON 推播請求，使用 shared secret 驗證 |
| PostgreSQL | 保存裝置 token、通知工作及各裝置 delivery 狀態 |
| Push Worker | 輪詢工作、呼叫 FCM、處理重試及無效 token |
| Firebase Cloud Messaging | 發送 Android 通知，並透過已設定的 APNs key 轉送 iOS 通知 |
| Flutter App | 儲存住戶卡號、註冊 FCM token、接收並顯示通知 |

## 裝置註冊流程

1. App 完成卡號設定並取得 Firebase token。
2. App 呼叫 `POST http://211.23.22.158:7004/v1/devices`。
3. 請求帶入完整卡號、`android` 或 `ios` 平台及 Firebase token。
4. 服務器依 `platform + push_token` 更新或新增裝置，並更新 `last_seen_at`。
5. Firebase token 更新時，App 會以相同卡號重新註冊。

裝置註冊 API 使用 `X-API-Key`。API key 會存在 App 二進位檔中，只能視為基本門檻，不能代替使用者身分驗證。

## 推播處理流程

1. 發送端透過 TCP 7002 或 `POST /v1/push` 提交完整卡號、標題、內容與選用 data。
2. Repository 在單一資料庫交易中建立 notification，並為所有相符的有效裝置建立 delivery。
3. 如果卡號沒有有效裝置，交易會移除 notification 並回覆錯誤。
4. Worker 預設每秒取得一筆工作，使用 `FOR UPDATE SKIP LOCKED` 避免重複處理。
5. Android 與 iOS 目前都使用 Firebase HTTP v1；Firebase 再將 iOS 通知交給 APNs。
6. Firebase 接受後，delivery 標記為 accepted；token 無效時會移除對應 device。
7. 暫時性錯誤採指數退避，最多嘗試 8 次，間隔上限 3600 秒。
8. 所有 delivery 完成後，notification 會被刪除，其 delivery 透過 cascade 一併清除。

Firebase 或 APNs 回覆接受，只代表推播供應商已接收訊息，不保證手機已顯示或使用者已讀取。目前系統沒有 App 回報的 delivery/read acknowledgement。

## 資料庫結構

### devices

保存卡號、平台、Firebase token、有效狀態及最後註冊時間。`platform + push_token` 唯一，同一張卡可對應多台裝置。

### notifications

保存待處理或失敗的通知工作，包含卡號、標題、內容、data、嘗試次數、狀態與下次重試時間。

### deliveries

保存一筆 notification 對每台目標裝置的狀態與 token snapshot。裝置被刪除時仍能保留當次 delivery 資訊，直到通知工作完成。

成功完成的 notification 與 deliveries 不作永久歷史保存。若需要稽核、送達報表或查詢歷史，應另建不可變的推播紀錄表，不應改變現有 queue 表的生命週期。

## 部署位置與設定

| 項目 | 路徑或名稱 |
|---|---|
| 應用程式 | `/opt/idtag-push` |
| Python 虛擬環境 | `/opt/idtag-push/.venv` |
| systemd 服務 | `idtag-push.service` |
| systemd unit | `/etc/systemd/system/idtag-push.service` |
| 環境設定 | `/etc/idtag-push.env` |
| Firebase service account | `/etc/idtag-push/firebase-service-account.json` |
| PostgreSQL 資料庫 | `idtag_push` |
| 執行帳號 | `idtagpush` |

`/etc/idtag-push.env` 包含資料庫密碼、API key、Socket secret 與 Firebase 設定，權限應維持 `0600`。Firebase JSON、APNs `.p8`、`.env` 與任何正式 secret 不得提交版本庫。

## 服務管理

```bash
sudo systemctl status idtag-push --no-pager
sudo systemctl restart idtag-push
sudo systemctl enable idtag-push
sudo journalctl -u idtag-push -f
```

確認監聽端口：

```bash
sudo ss -lntp | grep -E ':(7002|7003|7004) '
```

正常狀態：

```text
0.0.0.0:7002  Python TCP Socket
0.0.0.0:7003  sshd
0.0.0.0:7004  Python FastAPI
```

## PostgreSQL 維運

```bash
sudo -u postgres psql -d idtag_push
```

```sql
\dt

SELECT platform, card_number, active, last_seen_at
FROM devices
ORDER BY updated_at DESC;

SELECT id, card_number, title, status, attempts, next_attempt_at
FROM notifications
ORDER BY created_at DESC;

SELECT d.platform, d.status, d.last_error, d.updated_at,
       n.card_number, n.title
FROM deliveries d
JOIN notifications n ON n.id = d.notification_id
ORDER BY d.updated_at DESC;
```

不要直接修改 token 或工作狀態。人工重送、刪除失敗工作或清除裝置前，應先備份相關資料並確認影響範圍。

## 安全與後續改善

目前可運作，但正式長期維運應安排以下改善：

- 7002 為明文 TCP，至少應在 Zyxel 防火牆限制允許的來源 IP，較佳做法是改用 VPN 或 TLS。
- 7004 為明文 HTTP，應配置網域與可信任 HTTPS 憑證。
- App 內的 API key 可被反編譯取得，後續應以住戶登入憑證或一次性註冊機制取代。
- SSH 應改用金鑰登入、限制來源 IP，並停用對外密碼登入。
- Ubuntu 18.04 與 PostgreSQL 10 應納入升級計畫，升級前先建立 VM 與資料庫備份並完成相容性驗證。
- 若業務需要證明手機顯示或使用者已讀，需新增 App acknowledgement API；FCM 200 不能作為已讀證明。
